# Изменения карточек без polling

Открытая доска подписывается на `GET /api/v1/boards/{boardId}/tasks/events`.
SSE читается через авторизованный `fetch`, поэтому Bearer-токен остаётся в заголовке,
а обновление токена использует существующий auth-транспорт.

После сохранения задачи, паузы, запрета или связи транзакция вызывает PostgreSQL
`pg_notify` с идентификатором задачи. Откатившаяся транзакция не публикует событие.
Каждый экземпляр API с подписчиками держит один общий `LISTEN` через
`DATABASE_URL_UNPOOLED`. Пулерное подключение для LISTEN не подходит:
[ограничения Neon](https://github.com/neondatabase/website/blob/main/content/docs/connect/connection-pooling.md).
Новая служба и дополнительные переменные окружения не нужны.

При удалении задачи транзакция отправляет `board:<boardId>` в тот же канал.
Подписчики этой доски получают `ready` и заново загружают список. Связанные
задачи получают обычные уведомления: число связей и признак блокировки пересчитываются.

На уведомление экземпляр API один раз загружает изменённую и связанные карточки,
заново проверяет членство зрителей и рассылает карточки только по соответствующим
доскам. Фронт записывает их в TanStack Query cache, а зависимые запросы помечает
устаревшими без немедленного массового перезапроса. Собственные оптимистичные
переносы защищены: события во время мутации приводят к сверке после её завершения.

## Восстановление соединения

- `ready` приходит после установки LISTEN. Фронт сверяет снимок доски, чтобы
  получить изменения между первоначальной загрузкой и подпиской.
- `tasks.changed` содержит `items: TaskCard[]` и `serverTime`. Обычный перенос
  другого пользователя не вызывает GET доски.
- Heartbeat раз в 15 секунд поддерживает поток и не обращается к базе.
- Скрытая вкладка и offline закрывают подписку; возвращение восстанавливает её.
- Обрыв вызывает повтор с увеличением задержки и случайной добавкой. После
  восстановления снова приходит `ready`; история событий на сервере не хранится.
- Поток закрывается через 4 минуты или раньше, при истечении access-токена.
  Для API в `vercel.json` установлен `services.api.functions["src/index.ts"].maxDuration: 300`, чтобы успевать закрыть
  поток до лимита [Vercel Functions](https://vercel.com/docs/functions/configuring-functions/duration).
- После ухода последнего зрителя экземпляр API закрывает LISTEN-подключение.

Это убирает запросы доски каждые 3 секунды. Остаются подключение, разовая сверка
при подключении/восстановлении и запись изменений. Открытый LISTEN удерживает
соединение с Neon, пока есть зрители; число подключений зависит от числа активных
экземпляров API. При горизонтальном масштабировании важно учитывать лимит прямых
подключений базы.

## FSD

`shared/api/subscribe-events` отвечает за SSE, разбор потока и переподключение.
`entities/task/api/task-events` проверяет контракт событий и принадлежность доске.
`features/board/sync-tasks` управляет подпиской экрана, обновлением кэша и сверкой.
Общие схемы событий находятся в `packages/contracts`.

## Проверка после деплоя

Открыть одну доску в двух браузерах под разными участниками. Перенос, создание,
пауза и изменение блокера должны отражаться во втором браузере без GET всей доски.
В Network должен оставаться открытый запрос `/tasks/events`; heartbeat не должен
создавать новые запросы. Проверить восстановление после offline и скрытия вкладки,
а также удаление зрителя из участников. Эти проверки на живом Neon/Vercel дополняют
локальные тесты PGlite и потокового транспорта.
