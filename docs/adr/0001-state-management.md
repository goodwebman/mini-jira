# ADR-0001. Отдельный стейт-менеджер не нужен

Статус: принято · 14.11.2026

## Вопрос

Подключать ли Redux Toolkit, MobX или Zustand во фронтенд mini-jira.

## Что на самом деле хранит приложение

| Состояние                                              | Доля  | Скоуп                           | Механизм                                                                                     |
| ------------------------------------------------------ | ----- | ------------------------------- | -------------------------------------------------------------------------------------------- |
| Данные сервера: доски, задачи, спринты, KPI, профиль   | ~90 % | кэш запросов                    | TanStack Query: дедупликация, отмена, ретраи, инвалидация по тегам, оптимистичные обновления |
| Сессия                                                 | 1 шт. | global                          | `authService` (внешний стор) + `useSyncExternalStore`                                        |
| Текущая доска (сводка меню, KPI по умолчанию)          | 1 шт. | global в пределах сессии        | `createStore` + DI-провайдер в `RequireAuth`, `key={user.id}`                                |
| Фильтры доски, колонка на телефоне, подсветка задачи   | 1 шт. | cross-module: роуты одной доски | `createStore` + DI-провайдер в `BoardScope`, `key={boardId}`, только в памяти                |
| Фильтры «Моих задач», выбранные доска и спринт KPI     | —     | адрес                           | `useSearchParams`: ссылкой можно поделиться, работает «Назад»                                |
| Черновики форм, открытые диалоги, поиск в списке досок | —     | module / компонент              | `useState`                                                                                   |

Клиентского состояния, которое живёт дольше одного компонента, — три небольших стора. Всё остальное — кэш сервера, адрес или локальный `useState`.

## Решение

Стейт-менеджер не подключаем. Серверное состояние — TanStack Query (уже в проекте), клиентское — `createStore` из `shared/lib/store` (иммутабельный снапшот + подписка) и DI-провайдеры по скоупам из `shared/lib/di`.

## Почему

1. **Серверное состояние уже решено.** Redux без RTK Query заставил бы заново писать кэш, инвалидацию и защиту от гонок, а RTK Query дублировал бы TanStack Query. MobX и Zustand серверное состояние не решают вовсе — его всё равно пришлось бы держать в TanStack Query.
2. **Клиентское состояние скоупное, а Redux и Zustand по умолчанию глобальные.** Фильтры доски 9 не должны жить, пока пользователь смотрит KPI, и не должны всплывать у следующего пользователя на том же компьютере. С глобальным стором это ручные `reset()` в нужных местах. Со скоупом по роуту жизненный цикл бесплатный: React размонтировал провайдер — стор собрал GC; сменилась доска — новый `key` и новый экземпляр. Zustand для скоупов рекомендует ровно то же: `createStore` + контекст.
3. **Примитив стандартный.** `useSyncExternalStore` — официальный API React для внешних сторов; на нём построены react-redux 8+ и Zustand 4+. Наш `createStore` — около 30 строк с тем же контрактом (`getSnapshot`/`subscribe`), тестируется без React и не даёт tearing в concurrent-режиме.
4. **Включён React Compiler.** Он мемоизирует по ссылочному равенству и рассчитывает на иммутабельность. MobX построен на мутабельных observable и отслеживании чтений внутри `observer` — с компилятором это требует оговорок и проверки каждого компонента. Наши снапшоты иммутабельны.
5. **Цена.** RTK + react-redux ≈ 13–15 KB gzip, MobX + mobx-react-lite ≈ 17–20 KB gzip плюс обучение команды и правила работы с observable. Zustand почти бесплатен по весу (≈1 KB gzip) и дал бы то, чего у нас нет: селекторы и готовый `persist` с версиями схемы.
6. **Отладка.** Серверное состояние видно в TanStack Query Devtools; клиентского — десяток полей, их проверяют юнит-тесты сторов.

## Чем платим

- **Нет селекторов.** `useBoardWorkspace()` возвращает весь снапшот, и подписчик перерисовывается от любого поля. Сейчас стор маленький, а подписчик один — экран доски; обёртки, которым нужен только `boardId`, читают стор через `useBoardWorkspaceStore()` без подписки. Если появится тяжёлый подписчик на одно поле, понадобится `useStore(store, selector)` поверх `useSyncExternalStore` (около десяти строк) или переход на Zustand.
- **Нет готовой персистентности.** Фильтры доски намеренно живут только в памяти: так скоуп совпадает с жизнью роутов, и чужие фильтры не всплывают у следующего пользователя. Текущей доске хватает `createStoragePersistence` с разбором чужих данных. Если сохранять придётся много и со сменой схемы, `persist` из Zustand окажется дешевле своего кода.
- **Своя дисциплина вместо библиотечной.** Иммутабельность снапшотов и отсутствие логики в компонентах держатся на ревью и тестах сторов, а не на ограничениях библиотеки.

## Когда пересмотреть

- офлайн-режим или локальная очередь изменений с синхронизацией;
- undo/redo, совместное редактирование в реальном времени с большим клиентским состоянием;
- три и больше несвязанных глобальных клиентских стора со сложными производными данными;
- нужна отладка клиентской логики «путешествием во времени».

Первый кандидат тогда — Zustand: контракт тот же, переход локальный — заменить реализацию `createStore` в `shared/lib/store`, провайдеры и хуки страниц не меняются.
