# Как разбирать ошибки mini-jira в Sentry

## Текущая конфигурация

Организация: `mini-jira`. Для frontend используется проект `mini-jira-web`;
для API выбирайте Node.js-проект, DSN которого записан в `apps/api/.env`.
Локальные события имеют environment `development`, на Vercel environment
берётся из `VERCEL_ENV`, если не задан явно.

DSN и токен source maps уже проверены живой отправкой. Frontend из браузера
и API получили HTTP 200 от ingest. Source maps загружаются при production-сборке,
а публичные `.map` удаляются. Ошибка загрузки карт теперь останавливает сборку.

Для локального запуска:

```powershell
rtk npm run dev
```

В текущих локальных `.env` API использует `PORT=3001`, а Vite —
`API_PROXY_TARGET=http://localhost:3001`. Frontend открывается на
`http://localhost:5173`. Это dev-настройки; Vercel rewrite не меняется.
После изменения API `.env` перезапустите сервер.

Устранить текущий сбой базы можно только реальными строками Neon:
в `apps/api/.env` пока стоят примерные `DATABASE_URL` и
`DATABASE_URL_UNPOOLED` с пользователем `user` и паролем `password`.
Скопируйте подключения из Neon → Connect: пулерное для приложения,
прямое для миграций. Сначала проверьте `/api/v1/health`; затем для новой
базы примените миграции командой `rtk npm run db:migrate`.
Не запускайте миграции против неизвестной базы и не передавайте пароль в чат.

## Как найти событие

1. Откройте Sentry и выберите организацию `mini-jira`.
2. Перейдите в **Issues**. Для начала выберите оба проекта и период **24h**.
3. Выберите environment **development** для локальной проверки.
   Если ничего не видно, временно выберите все environments и увеличьте период.
4. Уберите фильтр `is:unresolved`, если нужная ошибка уже была решена или архивирована.
5. Для наших проверок ищите по тексту `Mini Jira Sentry frontend live verification`
   или `Mini Jira Sentry API live verification`.

**Issue** — группа похожих ошибок. **Event** — конкретное возникновение.
Один и тот же баг у трёх пользователей может дать один Issue и несколько Events.
Счётчик Events показывает повторы, Users — число идентифицированных пользователей.
До входа пользователя ID может отсутствовать.

Страница Issue может показывать рекомендованное событие, а не последнее.
Для свежей проверки выберите последнее событие и проверьте его время.
На Free-плане кнопка View More Events может отсутствовать.
Источник по навигации интерфейса:
[Sentry Issue Details](https://docs.sentry.io/product/issues/issue-details/).

## Как понять, где и почему упало

Читайте конкретное событие в таком порядке:

| Поле                     | Что проверять                                                |
| ------------------------ | ------------------------------------------------------------ |
| Project                  | Ошибка в браузере или на API                                 |
| Environment              | Локальная разработка, preview или production                 |
| Timestamp                | Совпадает ли с моментом вашего действия                      |
| Release                  | Какая сборка выполнялась; на Vercel — commit SHA             |
| Exception type / message | Непосредственная причина сбоя                                |
| Stack Trace              | Файл, функция и строка, где ошибка возникла                  |
| Tags → source            | Как ошибка попала в мониторинг                               |
| Tags → http.status_code  | HTTP-статус для ошибок нашего HTTP-клиента и API             |
| Tags → request_id        | Общий идентификатор HTTP-запроса для поиска в обоих проектах |
| Contexts → http          | Для API: метод и шаблон маршрута                             |
| Contexts → correlation   | Для API: requestId, совпадающий с ответом и серверным логом  |
| Contexts → react         | Стек React-компонентов для ErrorBoundary                     |
| User                     | Внутренний ID пользователя, если он авторизован              |
| Breadcrumbs              | Предшествовавшие запросы, навигация и auth-события           |

Значения `source` в текущем приложении:

| source              | Источник                                                            |
| ------------------- | ------------------------------------------------------------------- |
| `api`               | Неожиданный серверный сбой или явный AppError 500                   |
| `query`             | Окончательная ошибка запроса TanStack Query после повторных попыток |
| `mutation`          | Ошибка мутации TanStack Query                                       |
| `react`             | Ошибка rendering, пойманная ErrorBoundary                           |
| `connectivity-test` | Ручной тест подключения из предыдущей проверки                      |
| Отсутствует         | Например, глобальная JS-ошибка или необработанный Promise rejection |

Начинайте со своего кода в Stack Trace. Если верхний кадр относится к SDK,
React или драйверу БД, найдите ближайший кадр приложения, который его вызвал.
Frontend source maps должны раскрывать TypeScript/TSX и исходные координаты.
Если виден только `assets/index-*.js`, проверьте успешность загрузки карт,
выбранный release и то, что событие пришло из соответствующей сборки.
У старых тестовых событий из временной консоли стек может указывать на eval.

Для ошибок Drizzle SQL и параметры намеренно не передаются. Обычно видна
причина от драйвера, например `NeonDbError: password authentication failed`.
Это означает отказ базы по учётным данным. Изменение DSN Sentry такое не исправит.

## Как связать frontend, API и конкретное действие

Пример: пользователь нажал «Сохранить», запрос завершился HTTP 500.

1. В браузере откройте **DevTools → Network**, повторите действие и выберите
   неуспешный запрос к `/api/v1/...`.
2. Запишите его метод, адрес, время, статус и **Response Headers → X-Request-Id**.
   Наш API также возвращает этот ID в JSON как `error.requestId`.
3. В Sentry выберите оба проекта и введите:

   ```text
   request_id:СКОПИРОВАННЫЙ_ID
   ```

4. В API-событии изучите `source=api`, `Contexts → http → method/route`,
   сообщение причины и Stack Trace. Это объясняет, какой обработчик упал.
5. Во frontend-событии смотрите `source=query` или `mutation` и тот же ID.
   Это показывает, что браузер получил ошибку именно от этого запроса.
6. В stdout API или логах Vercel найдите тот же `requestId`.

Эта связь применяется к `HttpError` из нашего `apiClient`. Авторизационный
транспорт возвращает `AuthError` без requestId: у таких ошибок frontend
`request_id` может отсутствовать. Для них сопоставляйте время, внутренний user ID
и auth-маршрут в API-событии. Общий HTTP-статус в браузере смотрите в Network.

Для поиска по конкретному источнику:

```text
source:api
source:query
source:mutation
source:react
http.status_code:500
```

Каждую строку можно использовать отдельно; фильтры можно сочетать, например:

```text
source:api http.status_code:500
```

**Один failed request не обязательно создаёт два события.** Frontend-событие
появляется, если ошибка дошла до query/mutation cache. Наш health-check из
терминала создаёт только серверное событие. При повторных попытках запросы
получают разные IDs; frontend сохраняет ID последнего неудачного ответа.
Если ответ вообще не получен (offline, DNS, timeout), серверного request ID нет.

Распределённый tracing не подключён. Связь frontend/API выполняется через
request_id, а не через дерево spans. Автоматический сбор HTTP headers/body
выключен; query/mutation payload и значения форм не добавляются в контекст.
Sanitizer очищает известные поля секретов и формы их записи в тексте, но
не распознаёт любые персональные данные в произвольном сообщении ошибки.
Не включайте пароли, токены и пользовательский контент в error.message/tags.
Поэтому содержимое формы по событию восстановить нельзя; для контекста
используйте маршрут, внутренний user ID, время и безопасное воспроизведение.

## Что означает отсутствие события

- В development нужны DSN и соответствующий `*_SENTRY_ENABLED=true`.
  Для API переменная называется `SENTRY_ENABLED`, для frontend — `VITE_SENTRY_ENABLED`.
- Ожидаемые обработанные 4xx, отмена запроса и смена сессии отфильтрованы.
- Не всякий console.error является исключением: консольные сообщения не отправляются.
- Ошибки, пойманные прикладным кодом и не переданные мониторингу, автоматически
  не становятся Sentry-событиями. Известные точки интеграции перечислены выше.
- Проверьте проект, environment, время, архивные/решённые issues и бесплатную квоту.
- Для frontend проверьте Network: envelope-запрос мог быть заблокирован расширением/CSP.
- Полученный Event ID и `flush=true` сами по себе не гарантируют наличие Issue:
  окончательная проверка — событие в Sentry и успешный ответ ingest.

## Действия после исправления

Воспроизведите проблему, исправьте её причину, проверьте сценарий тестом,
соберите и разверните новую версию. Затем повторите действие и проверьте,
что запрос успешен и новые события этой ошибки не появляются.
После этого отметьте Issue как Resolved. Само нажатие Resolved не чинит код.
Тестовые connectivity-события можно архивировать, чтобы они не мешали разбору.

Для email-уведомлений подпишитесь на Issue через значок колокольчика;
настройки уведомлений находятся в User Settings → Notifications.
Если создаёте отдельное правило оповещения, выбирайте нужные проект и environment,
чтобы локальные тесты не смешивались с production.
