# platform: граница между сервисом и окружением

[К ядру](../README.md)

В браузере есть вкладки, location, события online и localStorage. На сервере этого
нет, а в тесте хотелось бы самим решать, когда «вернулась сеть». Если AuthService
будет напрямую читать window, его станет трудно тестировать и невозможно безопасно
использовать при серверном рендеринге. Platform передаёт эти возможности через
небольшой интерфейс.

Это не эмулятор всего браузера: сеть стратегий, Web Crypto и часы отдельных
протоколов не обязаны проходить через AuthPlatform. Он изолирует перечисленные
ниже возможности, а не заменяет весь JavaScript runtime.

## Файлы и их роль

| Файл | Что делает | Что потеряем без него |
| --- | --- | --- |
| `types.ts` | Описывает AuthPlatform, AuthChannel, AuthMarkers, AuthResumeInfo | Сервис начнёт зависеть от конкретного браузера |
| `browser-platform.ts` | Подключает настоящие browser API | Не будет синхронизации вкладок и реакции на события браузера |
| `memory-platform.ts` | Даёт реализацию без DOM | Импорт/работа сервиса в Node и SSR потребуют window-заглушек |
| `local-locks.ts` | Очередь с именованными блокировками внутри экземпляра | Без Web Locks даже один экземпляр сможет параллельно менять cookie |
| `platform.test.ts` | Проверяет блокировки, маркеры, каналы и подписки | Поведение окружения останется вне тестов ядра |

## types.ts: что сервис просит у платформы

| Метод/поле | Для чего нужен |
| --- | --- |
| `now()` | Время для сроков, backoff и updatedAt сервиса |
| `origin()` | Текущий origin либо null; нужен проверке адресов |
| `isVisible()` | Не опрашивать профиль в скрытой вкладке |
| `withLock(name, task, { timeoutMs })` | Сериализовать операции с серверной сессией |
| `openChannel(name)` | Обмен сообщениями login/logout/kick между вкладками |
| `onResume(listener)` | Сверка после возвращения на вкладку или из bfcache |
| `onOnline(listener)` | Повтор работы после восстановления соединения |
| `navigate(url)` | Переход на серверный SSO start |
| `markers` | Несекретные флаги намерений, например pending-logout |

Подписки возвращают функцию отписки. Сервис собирает их и вызывает при destroy.
Открытый канал тоже должен закрываться. Иначе HMR будет оставлять старые слушатели,
которые реагируют на сообщения вместе с новым экземпляром.

## browser-platform.ts: обычная вкладка

`detectPlatform()` выбирает браузерную реализацию, если окружение похоже на BrowserScope,
иначе создаёт memory-platform. Обычно достаточно конструктора AuthService без platform.
Для теста либо собственного окружения фабрику можно вызвать явно.

BrowserScope описывает только используемые части location/document/navigator/storage/
BroadcastChannel. Это позволяет передать маленький fake scope вместо целого window.
Полноценным проверяющим типы контейнером окружения этот интерфейс не является:
пользовательская реализация обязана соблюдать контракт.

### Web Locks: очередь операций с общей cookie

Даже если access живёт в памяти одной вкладки, refresh-cookie общая. Рассмотрим:

```text
вкладка A: refresh ───────────── Set-Cookie с новым refresh A
вкладка B:       login B ── Set-Cookie B
```

Если операции выполнятся в таком порядке без блокировки, поздняя cookie A может
перезаписать результат входа B. Проверка epoch в JavaScript не откатывает cookie:
её браузер применяет сам. Поэтому bootstrap, login, refresh и серверный logout
пользуются одним именем Web Lock в пределах namespace сервиса.

LockManager держит блокировку до завершения Promise задачи. Таймер платформы
ограничивает ожидание получения lock, но не отбирает уже выданный lock у владельца.
Выполнение сетевой операции отдельно ограничивается таймаутом сервиса.

Если ожидание истекло, результат — AuthError timeout, а task не запускается.
Запускать её «для доступности» без занятой блокировки опасно: это возвращает гонку,
ради которой lock добавлен. Bootstrap сохраняет unknown и может попробовать позже;
login сообщит ошибку вызывающему экрану.

Если API отсутствует либо явно запрещён окружением (SecurityError/NotSupportedError
до получения lock), используется LocalLocks. Ошибка уже запущенной задачи не приводит
к повторному запуску через fallback. Произвольные ошибки Web Locks не маскируются.

**Ограничение:** fallback синхронизирует только этот экземпляр платформы. Другие
вкладки и отдельные экземпляры без общей реализации lock не связаны. Серверная
защита от повторного refresh всё равно обязательна, но она не заменяет атомарность
входа/выхода разных пользователей между вкладками.

### BroadcastChannel: уведомить, а не передать токен

Канал рассылает короткие сообщения login/logout/kick. Токены по нему не ходят.
После login другого пользователя получатель восстанавливает сессию через сервер.
После logout он может сразу закрыть локальный интерфейс.

Web Locks и BroadcastChannel решают разные задачи. Lock управляет очередностью
изменений cookie, канал сообщает остальным, что состояние изменилось.
Если BroadcastChannel отсутствует, openChannel возвращает null; мгновенного
межвкладочного уведомления не будет, и вкладка сверится при последующем запросе,
polling или возвращении на экран. Наличие API ещё не гарантирует, что политика
конкретного iframe разрешает его использование: SecurityError/NotSupportedError
конструктора также отключают канал. Для специальных окружений можно передать свою
AuthPlatform.

### Маркеры и localStorage

В storage записывается значение `1` для ключа pending-logout. Ни токена, ни пароля,
ни профиля там нет. Маркер нужен, потому что при отсутствии сети JS не может удалить
httpOnly-cookie. На следующем старте он сообщает: «Пользователь уже вышел, сначала
доведи отзыв до конца, не восстанавливай вход по оставшейся cookie».

Если storage недоступен, фабрика пытается хранить маркеры в Set в памяти. Такой
fallback не переживает перезагрузку страницы и не разделяется между вкладками.
Private mode, квоты и политики доступа нужно учитывать при реальном развёртывании.
Нельзя «улучшить» этот механизм записью access-токена рядом с маркером.

### События возврата и bfcache

При visibilitychange до visible отправляется resume с restoredFromCache=false.
При pageshow с persisted=true отправляется restoredFromCache=true. bfcache —
это сохранённая браузером страница вместе с её JS-памятью. Пока она лежала в кэше,
сессия в другой вкладке могла измениться, поэтому требуется восстановление/сверка.

Событие online говорит, что браузер считает сеть доступной. Это не доказательство,
что API отвечает: сервер может быть недоступен, и обычная обработка ошибок остаётся.
Навигация выполняется через location.assign; разрешённость URL проверяет сервис
через OriginPolicy до вызова платформы.

## local-locks.ts: аккуратная очередь в памяти

LocalLocks хранит для каждого имени Promise хвоста очереди. Новая задача ждёт
предыдущую. Разные имена не блокируют друг друга. Ошибка одной задачи не ломает
последующие; завершённые хвосты удаляются из Map, чтобы не копить имена.

Непростой случай — истёк таймаут ожидающего:

```text
A держит lock ────────────────────── завершилась
B ждёт ── timeout (B не запускается)
C ждёт ──────────────────────────── начинает после A
```

Нельзя считать отклонение B освобождением занятого A lock. Иначе C обгонит A.
Хвост очереди сохраняет зависимость от прежнего владельца даже после таймаута B.
Это проверяется отдельным регрессионным сценарием в platform.test.ts.

LocalLocks не убивает зависшую задачу и не делает её безопасной для повтора.
Он ограничивает ожидание следующего клиента; сами session-операции должны соблюдать
signal и дедлайн. Процесс или другая вкладка не увидят эту Map.

## memory-platform.ts: Node, SSR и простые тесты

Фабрика создаёт собственные LocalLocks и Set маркеров. Время берётся из Date.now,
видимость всегда true, origin берётся из options либо null. Канала нет, подписки
на online/resume ничего не делают. navigate бросает misconfigured: Node не может
перенаправить открытую страницу так же, как location.assign.

```ts
const platform = createMemoryPlatform({ origin: 'https://app.example.com' });
const auth = new AuthService({ strategy, platform, identify: (user) => user.id });
try {
  await auth.bootstrap();
  // Работа только в контексте одного серверного HTTP-запроса.
} finally {
  auth.destroy();
}
```

Для SSR нужен новый сервис на каждый входящий запрос. Общий singleton может
отправить токен одного посетителя в запросе другого. Кроме того, Node fetch сам
не получает cookie из входящего HTTP-запроса и не прокидывает Set-Cookie в ответ:
это отдельно реализует серверная API-обвязка. Memory-platform этого не делает.
Серверный redirect тоже превращается в HTTP-ответ на уровне приложения.

Для сложных тестов удобнее TestBrowser из [testing](../testing/README.md): он умеет
поднять несколько связанных «вкладок», вручную вернуть сеть и передвинуть часы.

## Как добавить другое окружение

Реализуйте AuthPlatform и передайте её в конструктор сервиса. Все методы должны
либо соблюдать описанный контракт, либо честно сообщать, что возможность отсутствует.
Для namespace выбирайте одно имя для экземпляров с общей серверной cookie и разное
для независимых систем входа. Одно имя не координирует разные browser origin:
между доменами Web Locks и BroadcastChannel не являются общим каналом.

При изменении платформы проверяйте порядок задач, timeout без выполнения task,
ошибку самой задачи без двойного запуска, очистку listeners и отсутствие токенов
в storage/channel. Тесты Node не заменяют проверку конкретной политики браузера.
