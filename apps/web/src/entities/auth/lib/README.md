# lib: как устроено ядро авторизации

[Назад к модулю auth](../README.md)

Эта папка отвечает на два вопроса: «Есть ли у приложения сессия?» и «Как безопасно
отправить запрос от имени текущего пользователя?». Здесь нет формы входа, React,
адресов ручек mini-jira или zod-схем сервера. Благодаря этому одну и ту же логику
можно подключить к другому интерфейсу и другому HTTP-клиенту.

Если оставить только `fetch` с заголовком `Authorization`, первый запрос обычно
сработает. Проблемы начнутся позже: токен истечёт, несколько запросов одновременно
попытаются его обновить, пользователь выйдет раньше ответа или в соседней вкладке
войдёт другой человек. Основная работа этой папки — правильно обработать такие
порядки событий, а не просто добавить заголовок.

## Словарь перед чтением кода

- **Аутентификация** — подтверждение личности. **Авторизация** — проверка прав.
  Название auth объединяет клиентскую работу с сессией; права всё равно проверяет API.
- **Access-токен** — короткоживущий пропуск к API. В mini-jira живёт 15 минут,
  передаётся как `Authorization: Bearer …` и хранится только в памяти.
- **Refresh-токен** — пропуск для получения нового access. В mini-jira JavaScript
  его не читает: браузер хранит httpOnly-cookie, сервер обновляет её через Set-Cookie.
- **Ротация** — замена использованного refresh новым. Это серверная операция.
- **Сессия** — текущий вход пользователя. Обновление access не обязательно начинает
  новую сессию, а выход и вход другого человека обязательно создают границу.
- **Snapshot** — доступный интерфейсу снимок состояния. В нём нет токенов.
- **Single flight** — несколько вызовов ждут одну общую выполняющуюся операцию.
- **Гонка** — результат зависит от того, какой из параллельных ответов придёт первым.

## Карта ответственности

```text
React / другие потребители
        │ getSnapshot, subscribe, login, logout
        ▼
   AuthService ───────────────► AuthStore: состояние и события
        │
        ├─ AuthStrategy: как восстановить/получить/обновить реквизиты
        ├─ AuthPlatform: locks, канал вкладок, события браузера, маркеры
        ├─ internal: ожидание, таймауты, backoff, очередь persistence
        └─ AuthPipeline ◄──── adapters ◄──── HTTP-клиент приложения
```

Далее разобраны все `.ts` в корне `lib`. Тестовые файлы описаны рядом с кодом,
который они проверяют.

## auth-service.ts: координатор

`AuthService<TUser, TLoginInput, TCredentials>` связывает части вместе.
Параметры типов означают соответственно профиль, данные входа и секретные
реквизиты стратегии. Например, профиль mini-jira — `Me`, а реквизиты Bearer —
объект с access-токеном. Сервису не требуется знать поля профиля; стабильный
идентификатор он получает через `identify(user)`.

### Публичные операции

| Метод | Когда вызывать | Что произойдёт |
| --- | --- | --- |
| `bootstrap()` | Один раз при старте | Восстановит сессию через стратегию; параллельные вызовы разделят Promise |
| `login(input)` | Вход, регистрация, SSO | Сериализует изменение серверной сессии, примет grant или выполнит разрешённый redirect |
| `establish(grant)` | Другой доверенный сценарий уже получил реквизиты | Установит новую сессию без повторного login-запроса |
| `logout()` | Пользователь нажал «Выйти» | Сразу очистит локальную сессию, затем попробует отозвать её на сервере |
| `kick(reason)` | Сервер сообщил об отзыве, блокировке и т. п. | Закроет локальную сессию и сообщит другим вкладкам; сам серверный logout не вызывает |
| `refreshUser()` | Нужен свежий профиль | Получит его через переданный `fetchUser`; параллельные вызовы объединяются |
| `patchUser(patch)` | Изменение профиля уже подтверждено API | Применит поля локально; `undefined` пропустит; не заменяет сохранение на сервере |
| `startPolling()` / `stopPolling()` | Включить/выключить фоновую сверку | По умолчанию раз в 180 секунд обновляет профиль видимой вкладки |
| `getSnapshot()` / `subscribe(listener)` | Чтение состояния и подписка UI | Совместимы с `useSyncExternalStore`; subscribe возвращает отписку |
| `on(listener)` | Реакция кэшей и другой инфраструктуры | Даёт события ready/login/logout/kick/renewed/user |
| `destroy()` | HMR, завершение SSR-запроса, демонтаж владельца | Снимет подписки и таймеры; не завершает серверную сессию |

`establish` — доверенная граница: сюда передают уже проверенный результат входа.
Это не способ принять произвольный JSON из URL. Сетевые ответы mini-jira сначала
проверяются в `entities/auth/api`, а сервер всё равно проверяет каждый access.

### Состояние и фаза — разные вещи

`status` — известно ли наличие сессии: `unknown`, `guest`, `authenticated`.
`phase` — что происходит сейчас: `idle`, `restoring`, `signing-in`, `renewing`,
`redirecting`. Можно оставаться `authenticated` и одновременно обновлять токен.
Ошибка сети не означает, что пользователь перестал существовать.

На холодном старте `401` и `403` переводят в `guest`. Другие ошибки сохраняют
`unknown` с причиной и запускают повтор bootstrap с растущей паузой. На refresh
уже открытой сессии только `401` вызывает kick; `403`, сеть, `429` и `5xx` сохраняют
сессию. Это различие важно для интерфейса и серверного контракта.

`user` может быть `null` при `authenticated`: некоторые стратегии сначала получают
реквизиты, потом догружают профиль. Нельзя выводить наличие сессии только из `user`.

### Как проходит защищённый запрос

1. Адаптер вызывает `prepare({ url, method })`. Проверяется адрес, при необходимости
   ожидаются bootstrap/сверка вкладок/refresh и выполняется упреждающее обновление access.
2. Стратегия возвращает заголовки и режим cookie. Рядом выдаётся `ticket` с номерами
   сессии и версии токена, но без самого токена.
3. Адаптер отправляет HTTP-запрос.
4. `settle(attempt, response)` оценивает ответ и его принадлежность текущей сессии.
5. Если нужен повтор, новый `prepare` получает `retryOf: first.ticket`, а запрос
   уходит заново с актуальными реквизитами. Повтор максимум один.

`execute` собирает эти шаги. `authService.fetch` уже использует `execute`, поэтому
в прикладном коде обычно не требуется самостоятельно вызывать prepare/settle.
Сеть и `5xx` бизнес-запроса автоматически не повторяются. Повтор выполняется по
решению auth-конвейера; сервер должен отвергать неавторизованный запрос до изменения
данных. Иначе повтор POST после `401` может повторить уже выполненное действие.

### Почему два счётчика

`epoch` меняется на границе сессии. Если запрос начал пользователь A, а теперь
вошёл B, результат A нельзя положить в интерфейс B или повторить с токеном B.
Такой результат отклоняется с `session_changed`; старый `401` просто игнорируется
для текущей сессии. Проверка выполняется и после асинхронной оценки ответа.

`version` меняется при замене реквизитов в той же сессии. Если два запроса получили
`401`, а первый уже обновил токен, второй повторится с готовым токеном, без ещё
одного refresh. Одного `epoch` для этого недостаточно.

Promise-поля `#bootstrapRun`, `#loginRun`, `#renewal`, `#userRefresh` объединяют
повторные вызовы внутри экземпляра. Web Locks сериализуют операции с общей cookie
между вкладками. Это разные механизмы: общий Promise не виден соседней вкладке.
При таймауте ожидания занятого lock операция отклоняется, а не обходит очередь.

### Что происходит при выходе без сети

Профиль и access очищаются сразу. В platform сохраняется несекретный маркер
`pending-logout`. На следующем старте сервис сначала пытается довершить logout,
а не восстанавливает сессию по ещё живой cookie. При возврате сети попытка также
повторяется. Этот маркер не содержит токена и не заменяет серверный отзыв сессии.

Если login завершился после выхода или destroy, полученный grant уже никому
не нужен. Отзыв такой «осиротевшей» сессии происходит внутри того же lock:
поздний Set-Cookie от logout не должен стереть cookie следующего пользователя.
Поздний SSO-result после выхода также не имеет права вызывать переход.

**Если убрать координатор:** каждый HTTP-клиент и экран начнёт отдельно решать,
когда обновлять токен и кому принадлежит ответ. Тестирование одной ветки входа
не защитит от гонок между несколькими запросами и вкладками.

## auth-store.ts: наблюдаемое состояние

`AuthStore` хранит snapshot, подписчиков состояния и подписчиков событий.
`patch` создаёт новый объект только при реальном изменении полей, а старый объект
не мутирует. Это нужно React: новый объект на каждом чтении вызывает лишнюю работу,
а изменение прежнего объекта может остаться незамеченным.

Заморозка `Object.freeze` поверхностная: вложенный объект `user` тоже нужно считать
неизменяемым. Меняйте профиль через `patchUser`/сервер, а не `snapshot.user.name = …`.

События доставляются очередью. Если слушатель A сам инициировал другое событие,
слушатель B сначала увидит исходное событие, затем новое. Ошибка одного слушателя
передаётся `onListenerError`, не прерывая остальных. Сам обработчик ошибок должен
быть надёжным и не бросать исключения.

`isSessionBoundary(event)` отмечает logout, kick и login с `identityChanged`.
Адаптеры кэша используют его, чтобы не сохранять данные предыдущего пользователя.
Обновление access в той же сессии не требует полного удаления кэша.

**Без store:** пришлось бы вручную синхронизировать состояние каждой страницы.
**Без событий границы:** следующий пользователь мог бы увидеть старые данные кэша.

## types.ts: общий договор частей

Этот файл описывает интерфейсы, а не выполняет сетевые запросы.

| Группа типов | Зачем нужна |
| --- | --- |
| `AuthState`, `AuthEvent` | Согласованный формат snapshot и событий |
| `AuthGrant`, `AuthRedirect` | Два результата входа: реквизиты или серверный SSO-переход |
| `AuthStrategy` и контексты | Контракт стратегии, включая signal и сохранённую сессию |
| `AuthTarget`, `AuthDecoration` | Адрес/метод запроса и способ его подписать |
| `AuthTicket`, `AuthAttempt` | Связь ответа с исходной сессией и версией токена |
| `AuthResponseInfo`, `AuthVerdict` | Единое представление ответа и решение стратегии |
| `AuthPipeline` | Минимальный договор адаптера с сервисом |
| `AuthPersistence`, `PersistedSession` | Необязательное внешнее хранение для других окружений |

TypeScript не проверяет серверный JSON во время выполнения. Поэтому эти типы
не заменяют zod в `api/` и проверки входящих сообщений в `tab-messages.ts`.
В браузерном экземпляре mini-jira persistence не подключён: токены не сохраняются
в localStorage. Контракт оставлен для окружений с защищённым хранилищем.

**Без общего договора:** стратегия и адаптер будут связаны неявными полями,
а несовпадения обнаружатся только при запросе пользователя.

## errors.ts: одинаковые ошибки для разных клиентов

`AuthError` добавляет к Error стабильный `code`, HTTP-статус, серверный `serverCode`,
`retryAfterMs` и подробности валидации. Например, `code: unauthorized` описывает
категорию, а `serverCode: INVALID_CREDENTIALS` объясняет конкретную причину API.

`AuthError.fromResponse` читает статус, Retry-After и при переданном reader — тело
ответа. Reader приложения должен валидировать JSON. `toAuthError` приводит fetch,
AbortError, TimeoutError и ошибки со status/response.status к единому виду.

`retryable` означает возможность повторной попытки, а не обещает автоматический
повтор любого POST. Сервис использует это семейство ошибок для разных задач;
повтор бизнес-запросов остаётся отдельным решением.

`toJSON` не включает `cause` и details. Сырые axios-ошибки могут содержать
`config.headers.Authorization`, поэтому они не сохраняются в cause. Это снижает
риск случайной записи секретов в лог, но не делает произвольный серверный текст
безопасным для публикации: не выводите целые request/config/credentials в телеметрию.

**Без нормализации:** один клиент сочтёт `403` выходом, другой — временной сетью,
а интерфейс будет зависеть от конкретной библиотеки запросов.

## origin-policy.ts: кому разрешено получить реквизиты

Origin — сочетание схемы, хоста и порта: `https://api.example.com` и
`https://api.example.com:8443` различаются. `OriginPolicy` разрешает подписывать
свой origin и явно перечисленные `trustedOrigins`; отдельно проверяет адреса SSO
через `redirectOrigins`. Разрешение читать API не выдаёт произвольному сайту доступ.

Конфигурация требует точных origin без масок и пути. Внешний HTTP запрещён,
кроме loopback для разработки либо явного `allowInsecureOrigins`.
`baseUrl` нужен для относительных URL там, где нет browser location, например в Node.

`sanitizeReturnTo` разбирает путь через URL и возвращает только локальное назначение.
Строки `//evil.example` и `/\\evil.example` могут означать внешний хост, хотя начинаются
со слеша. Проверки одного `startsWith('/')` недостаточно. Сервер обязан независимо
проверять `next`: клиентскую функцию злоумышленник может обойти.

Проверяется первоначальный адрес. Fetch-адаптер дополнительно запрещает redirect
подписанных запросов, чтобы не передать API-ключ на адрес из ответа `302`.
Ограничения Axios описаны в [README адаптеров](./adapters/README.md).

**Без этой части:** случайный запрос `auth.fetch` к чужому сервису мог бы раскрыть токен.
Она не удаляет секреты, которые вызывающий код сам вручную положил в headers.

## response-info.ts: общий вид HTTP-ответа

Fetch возвращает `Response`, axios — объект с `status`, `headers`, `data` и часто
бросает исключение на `401`. `describeResponse` приводит эти формы к маленькому
интерфейсу: `status`, `header(name)`, `json()`. `describeThrown` ищет ответ внутри
исключения. Если это обычная ошибка сети без ответа, возвращает `null`.

Тело читается по требованию; для Response используется clone, чтобы приложение
ещё могло прочитать оригинальное тело. Это не схема валидации серверных данных.
В `execute` результат без распознаваемого статуса считается не требующим auth-реакции;
нестандартному клиенту нужно передать собственные inspect/inspectError.

**Без нормализатора:** обработка `401` дублировалась бы для каждого клиента,
либо axios-исключения обходили бы refresh-конвейер.

## tab-messages.ts: короткий протокол между вкладками

Есть только три сообщения: login с идентификатором пользователя, logout и kick
с причиной. В канале нет access/refresh-токена или целого профиля.
Получив login другого пользователя, вкладка восстанавливает сессию через сервер,
а не доверяет присланным реквизитам.

`parseTabMessage(unknown)` проверяет поля во время выполнения. Канал может открыть
любой код того же origin, поэтому входящие данные нельзя считать типизированными.
Это проверка формата, а не защита от XSS: вредоносный скрипт на том же origin
уже имеет намного больше возможностей, чем отправка сообщения logout.

**Без протокола:** одна вкладка выйдет, а другая продолжит показывать старый профиль
до следующего запроса или сверки. Сам канал не заменяет Web Locks.

## index.ts: публичный вход в библиотеку

Переэкспортирует сервис, типы, стратегии, адаптеры и фабрики платформы.
Внешний код берёт их отсюда; так внутренний helper можно поменять, не переписывая
все импорты приложения. `testing/test-kit.ts` намеренно не экспортируется:
иначе production-зависимости могли бы случайно потянуть Vitest.

**Без публичного входа:** потребители начнут импортировать приватные файлы
и любое перемещение внутреннего кода станет массовым изменением приложения.

## Тесты и порядок чтения

`auth-service.test.ts` проверяет lifecycle, счётчики, single flight, границы сессий,
таймауты, вкладки, persistence, события и сбои. Тесты соседних папок уточняют
контракты стратегий, клиентов и платформы. Все тесты ядра работают в Node.

Для первого знакомства: `types.ts` → простая Bearer-стратегия → fetch-адаптер →
публичные методы AuthService → сценарии гонок в тестах. Не нужно сначала понимать
весь Digest, чтобы безопасно использовать Bearer в mini-jira.

## Границы гарантий

- Защита данных и прав остаётся на сервере. Клиентский status не является разрешением.
- HttpOnly мешает прочитать cookie, но XSS всё ещё может делать запросы из вкладки.
- Без Web Locks нет атомарности между вкладками; без BroadcastChannel нет мгновенного
  уведомления о выходе. Подробнее в [platform](./platform/README.md).
- Таймаут означает прекращение ожидания и отправку abort. Он не доказывает, что
  сервер не выполнил запрос. Стратегии обязаны передавать signal в обычный fetch.
- SSR требует отдельного экземпляра на запрос и явной передачи серверного контекста:
  memory-platform сама не копирует cookie пользователя в Node fetch.
