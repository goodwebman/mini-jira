# adapters: соединяем авторизацию с HTTP-клиентом

[К ядру](../README.md) · [К модулю auth](../../README.md)

Адаптер — переходник между двумя интерфейсами. AuthService умеет подготовить
реквизиты, оценить ответ и решить, нужен ли повтор. Но он не должен знать, как
устроены interceptors axios, queryFn TanStack или ошибка GraphQL. Это знает адаптер.

Представьте замену fetch на axios: способ входа и защита от гонок должны остаться
прежними. Если refresh встроить прямо в axios interceptor, другой клиент придётся
учить тому же самому, а ошибки двух реализаций начнут различаться.

## Что находится в папке

| Файл | Его задача | Если его убрать |
| --- | --- | --- |
| `fetch.ts` | Полный HTTP-конвейер поверх стандартного fetch | Придётся вручную подписывать, оценивать и повторять каждый запрос |
| `axios.ts` | Подключение конвейера через interceptors | Axios-запросы будут обходить автоматический refresh |
| `graphql.ts` | Превращение GraphQL UNAUTHENTICATED в эффективный 401 | Ответ HTTP 200 скроет истечение сессии от конвейера |
| `tanstack-query.ts` | Очистка кэша на границе сессии и политика retry | Данные старого пользователя могут остаться в кэше |
| `rtk-query.ts` | Сброс RTK Query на границе сессии | Redux-кэш продолжит содержать результаты прежнего входа |
| `adapters.test.ts` | Проверка контрактов и сетевых сценариев | Ошибка переходника может остаться незаметной при исправном ядре |

Адаптеры не импортируют сами библиотеки. Вместо этого принимают небольшие
структурные интерфейсы, например QueryClientLike с методом clear. Это позволяет
использовать ядро без установки axios, Redux и TanStack одновременно.

## Один конвейер для всех клиентов

```text
prepare(target) → отправить запрос → settle(ticket, response)
                                            │
                         done ──────────────┤
                         retry → prepare(retryOf) → повторить один раз
```

`prepare` возвращает `headers`, `credentialsMode` и `ticket`.
Ticket не содержит токена: это информация о том, в какой сессии ушёл запрос.
Его нельзя потерять или создать заново из текущего snapshot при получении ответа:
пока шла сеть, пользователь уже мог поменяться.

`settle` возвращает `done` либо `retry`. Решение обновлять токен принимается
в сервисе/стратегии, а не в адаптере. `execute` уже реализует последовательность
с максимум одним повтором. Самостоятельному адаптеру достаточно использовать его,
если клиент позволяет обернуть отдельный вызов.

## fetch.ts подробно

`createAuthFetch(auth, options)` возвращает функцию с привычными аргументами fetch.
Готовый `authService.fetch` уже создан таким способом, создавать второй не нужно.

```ts
const response = await authService.fetch('/api/v1/boards', { signal });
if (!response.ok) throw await AuthError.fromResponse(response);
const boards = await response.json();
```

Fetch обычно не бросает исключение на `404`, `401` или `500`: он возвращает Response.
Адаптер сохраняет это поведение. Он может обновить токен и повторить `401`, но если
окончательный ответ неуспешный, его status всё ещё нужно проверить в API-функции.

### Почему создаётся Request

Единый Request объединяет URL, method, headers, body и signal независимо от того,
передал вызывающий код строку, URL или готовый Request. Относительный адрес
разрешается через `auth.resolveUrl`. Перед подписанной попыткой source клонируется:
тело запроса обычно можно прочитать только один раз, а для повтора нужно такое же тело.

Это помогает для JSON, FormData и других клонируемых тел. Уже использованный Request
не становится пригодным повторно. Большие потоковые тела требуют отдельного решения:
клонирование потоков может буферизовать данные, и универсальный повтор загрузки
не гарантируется. Не обещайте бесконечные retry для stream upload.

Если первая попытка будет заменена повтором, её Response body отменяется.
Иначе ненужный поток может продолжать держать сетевые ресурсы.

### Redirect и чужие адреса

Для подписанного запроса всегда устанавливается `redirect: 'error'`, даже если
вызывающий код указал follow. Причина: API может ответить `302` на внешний сайт.
Нестандартные заголовки вроде X-API-Key нельзя отдавать этому сайту. Подписанный
API должен возвращать данные/статус, а навигацией OAuth занимается login redirect.
При redirect fetch отклонит Promise; это ожидаемое ограничение безопасности.

Для чужого origin сервис не добавляет реквизиты. Но он не стирает заголовки и cookie,
которые вызывающий код намеренно задал сам. `skipAuth: true` также означает «не
добавлять авторизацию сервиса», а не «сделать запрос анонимным независимо от init».

### Отмена и повтор

Signal относится к конкретному запросу. Если компонент размонтировался, его
ожидание общего refresh можно отменить, не отменяя refresh для других запросов.
Сетевые login/refresh самой стратегии идут обычным fetch с собственным signal;
передача `authService.fetch` внутрь refresh создаст ожидание refresh самого себя.

Адаптер не повторяет потерянные POST по любой сетевой ошибке. Он повторяет ответ
авторизационного конвейера. Для операций с изменением данных сервер обязан сначала
проверить доступ; для прикладных повторов может отдельно требоваться idempotency key.

## axios.ts подробно

```ts
const client = axios.create({ baseURL: '/api/v1' });
const detach = attachAuthToAxios(authService, client);
// при завершении владельца или HMR:
detach();
```

Request interceptor вызывает prepare и добавляет заголовки. Response interceptor
обрабатывает и обычный response, и rejected promise: axios по умолчанию бросает
на неуспешный статус. Иначе именно `401`, ради которого нужен refresh, обошёл бы
проверку. Адаптер поддерживает и изменённый validateStatus с fulfilled-ответами.

В config записываются `__authTicket` и `__authRetryOf`. Они строковые, потому что
axios при mergeConfig может потерять нестандартные Symbol-поля. Потеря ticket
сломала бы защиту от ответа предыдущей сессии и ограничение повторов.

Заголовки ставятся через `.set`, если это AxiosHeaders, либо через обычный объект.
URL определяется через getUri, чтобы учесть baseURL/params средствами самого клиента.
Отписка удаляет оба interceptor; повторное подключение без detach создаст дубли.

### Отличия от fetch, которые нельзя скрыть

- В браузере axios обычно использует XHR. Его автоматические redirects нельзя
  надёжно перехватить теми же настройками, что Fetch redirect:error. Защищённый
  API для этого клиента не должен перенаправлять на чужие origin, особенно при
  API-ключах/CSRF/custom headers. Для строгого запрета redirect используйте fetch.
- `withCredentials: false` не равен Fetch `credentials: 'omit'`: XHR продолжает
  отправлять same-origin cookie. Поэтому Basic/Digest через axios не получают
  полной изоляции cookie и встроенной browser HTTP-auth, которую задаёт fetch.
- API-ключ или Authorization, прописанный вручную в defaults/config, не исчезнет
  из-за skipAuth или проверки первоначального URL сервисом.
- Адаптер не умеет заново создавать произвольный одноразовый Node stream в data.
  Тело должно поддерживать повтор или загрузка должна иметь отдельный протокол.

## graphql.ts: почему одного HTTP-статуса мало

GraphQL может вернуть `200 OK`, но положить отказ авторизации в errors:

```json
{ "errors": [{ "extensions": { "code": "UNAUTHENTICATED" } }] }
```

`graphqlEffectiveStatus` читает clone JSON-ответа и возвращает 401 для такого кода.
Оригинальное тело остаётся доступным GraphQL-клиенту. Другие ошибки, неверный JSON,
не-JSON content type и HTTP-статусы кроме 200 не превращаются в auth-ошибку.
Это не универсальный парсер всех GraphQL-протоколов: multipart/streaming требуют
другого inspect, а другой серверный code требует другой функции effectiveStatus.

```ts
const fetchGraphql = createAuthFetch(authService, {
  effectiveStatus: graphqlEffectiveStatus,
});
// Передайте fetchGraphql в fetch-опцию вашего GraphQL-клиента.
```

Сервер должен согласовать семантику: повтор GraphQL mutation безопасен только если
UNAUTHENTICATED означает, что операция не выполнена. Наличие частичных data вместе
с errors не делает повтор произвольной mutation автоматически безопасным.

## tanstack-query.ts: транспорт отдельно, кэш отдельно

`bindAuthToQueryClient` не выполняет запросы. Он подписывает queryClient.clear()
на границы сессии: logout, kick и вход другого пользователя. Сам queryFn должен
использовать authService.fetch. Один только bind не добавляет Authorization.

```ts
const unbind = bindAuthToQueryClient(authService, queryClient);
// В queryFn:
const response = await authService.fetch('/api/v1/boards', { signal });
if (!response.ok) throw await AuthError.fromResponse(response);
return response.json();
```

`shouldRetryQuery(failureCount, error, limit = 3)` запрещает повтор AuthError,
у которого retryable=false, и ограничивает число остальных попыток. Без проверки
response.ok неуспешный Response станет обычными данными, и retry-функция его не увидит.

При очистке удаляется кэш клиента целиком, в том числе общие данные. Если приложению
потребуется отдельный публичный кэш, это осознанно проектируют на уровне приложения.
Не заменяйте очистку приватного кэша одним invalidate: старые данные ещё могут отображаться.

## rtk-query.ts

Транспорт подключается через `fetchBaseQuery({ fetchFn: authService.fetch })`.
`bindAuthToRtkQuery(auth, store, api)` отдельно вызывает dispatch(resetApiState())
на границе сессии. Возвращает отписку. Ошибки RTK Query остаются в формате RTK:
адаптер не превращает автоматически каждый результат baseQuery в AuthError.

Очистка кэша защищает от уже сохранённых чужих данных; проверка epoch в конвейере
защищает от старого ответа, который ещё только летит. Нужны обе части.

## Как добавить свой адаптер

1. Определите фактические URL и method до отправки.
2. Используйте execute либо prepare/settle и сохраните исходный ticket.
3. Примените headers/credentialsMode и передайте signal в транспорт.
4. Приведите ответ и HTTP-исключение к AuthResponseInfo.
5. Повторите максимум один раз с retryOf, сохранив method/body/пользовательские headers.
6. Освободите ненужный ответ и верните результат в привычной клиенту форме.

Проверяйте отказ второго токена, поздний ответ после logout, параллельные `401`,
отмену одного ожидающего запроса, чужой origin и повтор тела. `adapters.test.ts`
даёт такие сценарии, но mock-клиенты не заменяют интеграционную проверку новой
версии настоящей axios/GraphQL/query-библиотеки.
