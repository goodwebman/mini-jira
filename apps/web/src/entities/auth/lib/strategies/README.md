# strategies: разные способы входа за одним интерфейсом

[К ядру](../README.md) · [К сетевым адаптерам](../adapters/README.md)

Стратегия описывает конкретный протокол: откуда взять реквизиты, как прикрепить
их к запросу и как понять отказ. Сервису не нужно знать, является ли секрет JWT,
API-ключом или хешем Digest. Поэтому новый протокол не требует переписывать
синхронизацию вкладок, снимки состояния и защиту от старых ответов.

Если убрать эту границу, в AuthService появятся ветки вида «если Bearer — refresh,
если cookie — CSRF, если Digest — nonce». Каждая новая ветка будет влиять на все
остальные. Здесь эти различия локализованы в отдельных файлах.

В mini-jira используется только BearerStrategy, дополненная withSsoRedirect.
Наличие остальных классов не означает, что приложение одновременно отправляет
Basic, Digest и API-ключ: это реализации для другого серверного контракта.

## Общий интерфейс AuthStrategy

| Метод                             | Обязателен | Что должен вернуть/сделать                                  |
| --------------------------------- | ---------- | ----------------------------------------------------------- |
| `restore({ stored, signal })`     | Да         | Grant текущей сессии либо null, если входа нет              |
| `login(input, { signal })`        | Да         | Grant либо AuthRedirect с адресом перехода                  |
| `decorate(credentials, target)`   | Да         | Заголовки и режим cookie для защищённого запроса            |
| `renew({ credentials, signal })`  | Нет        | Новые реквизиты; при отсутствии метода обновления нет       |
| `logout({ credentials, signal })` | Нет        | Серверный отзыв/очистка сессии; credentials могут быть null |
| `assess(response, credentials)`   | Нет        | pass / renew / retry / reject                               |

Grant — объект `{ credentials, user?, expiresInMs? }`. TTL передаётся в миллисекундах
от момента получения, не абсолютной датой. User можно не вернуть: тогда сервис
попробует fetchUser, если он настроен. Grant не помещается в UI snapshot целиком:
секретные credentials остаются в приватном состоянии сервиса.

Без assess сервис пропускает ответы кроме 401. Для 401 он выбирает renew, если
стратегия умеет обновляться, иначе reject. `retry` нужен для исправления реквизитов
без отдельного refresh, например при новом Digest nonce. Любой повтор ограничен
конвейером одним разом.

Все сетевые методы стратегий используют обычный fetch или API-callback с обычным
fetch. Нельзя передавать authService.fetch в refresh: конвейер начнёт ждать тот же
refresh, внутри которого вызван. Signal обязательно передавать в сеть.

## Карта файлов

| Файл                         | Протокол/задача                           | Если его убрать                                                        |
| ---------------------------- | ----------------------------------------- | ---------------------------------------------------------------------- |
| `bearer.strategy.ts`         | Access-токены с необязательным refresh    | Исчезнет текущий способ входа mini-jira                                |
| `jwt.ts`                     | Извлечение приблизительного срока JWT     | Обновление будет ориентироваться на 401, если TTL не передан явно      |
| `session-cookie.strategy.ts` | Серверная cookie-сессия и CSRF-header     | Придётся вручную добавлять режим cookie и CSRF к запросам              |
| `api-key.strategy.ts`        | Постоянный ключ в заголовке               | Нужен будет свой код проверки/подписи API-ключом                       |
| `basic.strategy.ts`          | HTTP Basic с проверкой учётных данных     | Старый API с Basic не подключится через общий сервис                   |
| `digest.strategy.ts`         | HTTP Digest challenge/response            | Нельзя будет работать с API, требующим Digest nonce                    |
| `sso-redirect.ts`            | Серверный SSO поверх основной стратегии   | Форма входа должна будет отдельно управлять переходами                 |
| `strategies.test.ts`         | Проверка протоколов и пограничных ответов | Исправность общего сервиса не докажет корректность заголовка/nonce/TTL |

Удаление неиспользуемой стратегии не ломает Bearer само по себе, если убрать
соответствующие экспорты/тесты. Но изменится публичный API переносимой библиотеки.

## bearer.strategy.ts: основной сценарий mini-jira

Bearer означает: тот, кто предъявил токен, получает связанные с ним права.
По умолчанию decorate возвращает `Authorization: Bearer <accessToken>`.
Стратегия не знает адресов API: они приходят через BearerApi.

```ts
const strategy = new BearerStrategy<User, LoginInput>({
  api: {
    login: (input, { signal }) => loginViaPlainFetch(input, signal),
    refresh: ({ signal }) => refreshViaPlainFetch(signal),
    logout: ({ signal }) => logoutViaPlainFetch(signal),
  },
});
```

Названия `loginViaPlainFetch` здесь условные: приложение реализует их самостоятельно,
проверяет response.ok и валидирует JSON. Реальная обвязка mini-jira находится
в `entities/auth/api/auth-api.ts`, а подключение — в `model/auth-instance.ts`.

### Два вида реквизитов

BearerCredentials содержит accessToken и refreshToken. В браузерном mini-jira
refreshToken равен null: это не отсутствие серверной сессии, а признак того, что
refresh доступен только браузеру как httpOnly-cookie. BearerApiContext передаёт
обоим callback текущие токены, если они вообще доступны в этом окружении.

Некоторые небраузерные API выдают refresh в JSON — контракт это допускает,
но не требует. Нельзя ради удобства переносить cookie-refresh mini-jira в localStorage.

### Восстановление и обновление

Если явно подключён persistence и сохранённый access ещё действителен по его
expiresAt, restore может использовать его. В противном случае вызывает refresh,
если он есть. При отсутствии refresh и сохранённой действующей сессии вернёт null.

При наличии api.refresh конструктор создаёт renew. Без api.refresh самого метода
renew нет: это важно, потому что сервис по его наличию выбирает поведение 401.
Logout аналогично присутствует только если api предоставляет отзыв.

Результат login/refresh преобразуется в grant. Непустой access без пробельных
символов обязателен; неверное значение даёт bad_response. Это минимальная проверка
формы, не проверка подлинности JWT: ответ mini-jira дополнительно валидируется zod.
Если refresh-ответ не прислал новый refreshToken в JSON, сохраняется прежний
JS-refresh, если он был. Для cookie-режима оба остаются null.

`formatHeaders` позволяет изменить заголовок для чужого API. Это не отменяет
проверку trustedOrigins и запрет redirect подписанных fetch-запросов.

### Что произойдёт на 401

```text
access истёк → API вернул 401 → один общий renew
             → новый access → один повтор исходного запроса
```

Если refresh тоже дал 401, сервис закроет сессию. Если refresh дал сеть/5xx/429/403,
сессия сохраняется, а обновления временно ограничиваются backoff или Retry-After.
Когда access ещё годен, запрос может продолжиться со старым access после сбоя
упреждающего обновления. Просроченный access при неуспешном renew не отправляется.

## jwt.ts: подсказка, когда обновлять, а не валидатор

`readJwtTtlMs` декодирует среднюю часть JWT, читает числовые exp и iat и возвращает
`(exp - iat) * 1000`. Если токен непрозрачный или payload не подходит — null.
Она не проверяет подпись, issuer, audience и разрешения. Подделанный payload не
даёт доступа к серверу: сервер должен выполнять настоящую проверку JWT.

Почему не просто exp - Date.now? Часы компьютера пользователя могут спешить.
Разница двух серверных значений задаёт приблизительную продолжительность жизни.
Но это не точный остаток: старый токен, полученный с задержкой, уже потерял часть
TTL. Для такого источника лучше передать точный expiresInMs из доверенной обвязки.
Серверный 401 остаётся окончательным сигналом, а сервис обновляется заранее с запасом.

Для opaque Bearer-токена без TTL упреждающего обновления не будет: renew запускается
после 401. Не нужно пытаться декодировать любой Bearer как обязательный JWT.

## session-cookie.strategy.ts: access-токена в JS вообще нет

Сервер может хранить сессию целиком у себя и авторизовать каждый запрос по cookie.
В этом режиме credentials — строковый маркер `cookie-session`, не настоящий секрет.
Restore вызывает api.getUser; login вызывает api.login; оба получают профиль.
Отдельного renew нет: отказ cookie означает необходимость нового входа.

```ts
new SessionCookieStrategy({
  api: { login, getUser, logout }, // Обычные HTTP-callback приложения.
  credentialsMode: 'same-origin',
  csrf: { headerName: 'X-CSRF-Token', readToken },
});
```

Для GET/HEAD/OPTIONS стратегия не добавляет CSRF-header. Для остальных методов
вызывает readToken и ставит заголовок, если токен найден. Важное ограничение:
если readToken вернул null, клиент не блокирует запрос. Сервер обязан отвергнуть
изменение данных без требуемой CSRF-проверки; наличие опции само по себе не защита.
Сами login/logout/getUser callbacks также должны выполнять серверные CSRF/Origin
требования — decorate не оборачивает их обычный fetch автоматически.

По умолчанию cookie идут same-origin. Для отдельного origin нужен include,
точный trustedOrigins, подходящие cookie-атрибуты и серверный CORS.
Отправка credentials ещё не означает, что SameSite разрешит cross-site cookie.

Без CSRF-контракта браузер может прикрепить cookie к запросу, который пользователь
не инициировал в вашем интерфейсе. HttpOnly решает чтение cookie скриптом,
а не все способы выполнения действий с этой cookie.

## api-key.strategy.ts: ключ в заголовке

По умолчанию ключ передаётся в X-API-Key, имя меняется через headerName.
`login({ apiKey })` принимает непустой ключ; provideKey позволяет получить его
при restore. Необязательный verify проверяет ключ на сервере и возвращает профиль.

Без verify сервис может стать authenticated только на основании наличия строки.
Это не подтверждение валидности ключа: первый запрос к серверу ещё может получить 401.
Проверка прав всё равно выполняется API. Обновления ключа здесь нет.

Ключ не помещается в URL: URL попадает в историю, логи и Referer. Но ключ,
зашитый в браузерный bundle, также нельзя считать секретом — его получит любой
посетитель страницы. Серверные API-ключи должны оставаться на сервере.

## basic.strategy.ts: имя и пароль в каждом запросе

Стратегия кодирует `username:password` в UTF-8/Base64 и отправляет Authorization Basic.
Base64 — обратимое представление, а не шифрование. HTTPS необходим.
Verify-callback обязателен: login проверяет заголовок на сервере и получает профиль.
Двоеточие в username отвергается, потому что оно разделяет имя и пароль.

В credentials хранится уже сформированный authorization, а не отдельный пароль.
Но это всё равно секрет, эквивалентный паролю для этого API. Сохранять его в лог
или browser storage нельзя. Restore всегда возвращает null: после перезагрузки
потребуется ввод снова. Клиентский logout не может отменить существование пароля
или отозвать уже известный другому человеку Basic-header.

Fetch credentials:omit уменьшает вмешательство cookie и встроенной HTTP-auth
браузера. Оно не удаляет явно переданный Authorization. У axios/XHR семантика
отличается — см. [ограничения адаптера](../adapters/README.md).

## digest.strategy.ts: challenge, nonce и подпись запроса

Digest нужен для API, которые отвечают WWW-Authenticate: Digest вместо выдачи токена.
Это более сложный протокол, который стоит выбирать только если его требует сервер.

### Последовательность входа

1. Обычный GET на verifyUrl без Authorization получает 401 с challenge.
2. Из challenge выбираются realm, nonce, algorithm, qop и при наличии opaque.
3. Вычисляется `H(username:realm:password)`. Этот secret хранится вместо пароля.
4. Из secret, метода, пути, nonce и счётчиков строится Digest-header.
5. Повторный GET с заголовком проверяет вход; parseUser может извлечь профиль.

Realm — область аутентификации сервера. Nonce — выданное сервером значение для
подписи. Cnonce — случайное значение клиента. Nc — счётчик запросов с данным nonce.
Opaque — непрозрачная строка сервера, которую нужно вернуть обратно.

Если verifyUrl ответил успешным статусом без challenge, стратегия считает настройку
ошибочной: по такому открытому адресу нельзя проверить пароль. Неверные данные
или неподдерживаемый challenge не должны превращаться в успешную сессию.

### Что поддерживается

- По умолчанию SHA-256 и его session-вариант SHA-256-sess.
- Qop=auth: подписывается метод и URI, но не всё тело запроса как при auth-int.
- Дополнительные hashers подключаются явно; MD5 не включён по умолчанию.
- Не-ASCII username передаётся через username*; кавычки и обратные слеши экранируются.
- Stale challenge с тем же realm обновляет nonce и разрешает один повтор.
- Authentication-Info nextnonce обновляет nonce для следующих запросов.

Это конкретная реализация части Digest, не обещание поддержки всех вариантов RFC:
auth-int и другие расширения не реализованы. Для другого сервера проверяйте его
точный challenge и поведение параллельных запросов.

### Зачем счётчик изменяется до await

Если два decorate одновременно начнут вычислять хеши и сначала уйдут в await,
они могут взять одинаковый nc. Поэтому counter увеличивается синхронно до первой
асинхронной операции, а значения для подписи сохраняются в локальные переменные.
Это защищает конкретные реквизиты одной вкладки, не объединяет Digest-состояние
между независимыми клиентами.

При смене nonce counter сбрасывается. Если сервер отклоняет второй запрос после
первого retry, сервис закрывает сессию вместо бесконечного пересчёта заголовка.
Секрет HA1 тоже чувствителен: его кража может позволить подписывать запросы в этом
realm. Хеш вместо plaintext не делает хранение в localStorage допустимым.

Digest работает через обычный fetch с credentials:omit и переданным signal.
При отдельном origin серверу нужно открыть для JS нужные заголовки, включая
WWW-Authenticate и Authentication-Info. Сам протокол не заменяет HTTPS.

## sso-redirect.ts: надстройка, а не ещё одно хранилище токенов

`withSsoRedirect(strategy, options)` оборачивает существующую стратегию.
Обычные login передаются ей без изменений. Вход `{ sso: 'google', returnTo: … }`
превращается в AuthRedirect через buildUrl. ReturnTo очищается sanitizer до
локального пути; сервис отдельно проверяет допустимость redirectTo.

```ts
const strategy = withSsoRedirect(new BearerStrategy({ api }), {
  buildUrl: (provider, returnTo) =>
    `/api/v1/auth/${provider}/start?next=${encodeURIComponent(returnTo)}`,
  defaultReturnTo: '/boards',
});
```

`provider` в этом примере должен быть ограничен приложением до поддерживаемых
провайдеров. TypeScript union помогает своим callers, но сервер обязан независимо
валидировать route/provider/next, OAuth state и ответ провайдера.

Код Google/GitHub обменивается на сервере, сервер ставит refresh-cookie и возвращает
браузер в приложение. На новой странице bootstrap получает access через обычный
refresh. Токены не передаются в returnTo, query string или BroadcastChannel.
Стратегия не обрабатывает серверный `?authError=`: это делает страница login.

Наличие декоратора не означает реализацию OAuth PKCE в браузере или поддержку
любого IdP. Серверный OAuth/BFF-контракт и регистрация клиента у провайдера остаются
за API. Без этой надстройки Bearer по паролю работает, но SSO вход сервисом не описан.

## Как выбирать и расширять

Сначала выясните контракт сервера. Для mini-jira уже выбраны Bearer + refresh-cookie
и серверный SSO. Нельзя сменить класс на SessionCookie и ожидать, что API само
начнёт авторизовывать обычные ручки через cookie с узким auth Path.

Новую стратегию добавляйте через AuthStrategy: restore/login/decorate, затем только
необходимые опциональные методы. Проверяйте успешный вход, 401/403/5xx, неверное
тело, отмену, срок жизни и сценарий без renew. Для сложной подписи используйте
фиксированные проверочные значения и отдельные тесты параллельных запросов.
Стратегия не должна импортировать React, библиотеку запросов или модель приложения.
