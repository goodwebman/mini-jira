# testing: как проверять авторизацию без настоящего браузера

[К ядру](../README.md)

Эта папка содержит `test-kit.ts`: общие инструменты unit-тестов. Она не используется
приложением и не экспортируется из `lib/index.ts`. Здесь намеренно есть импорт Vitest:
ограничение «ядро не зависит от UI/HTTP-библиотек» не означает, что тесты должны
обходиться без тестового раннера.

Главная цель — управлять порядком событий. Тест «login вернул пользователя» полезен,
но не отвечает, что произойдёт, если logout случился на середине login. Ждать
реальную медленную сеть для каждого такого сценария было бы долго и нестабильно.

## Что даёт test-kit.ts

| Экспорт                                 | Задача                                             | Чем пришлось бы заменить без него               |
| --------------------------------------- | -------------------------------------------------- | ----------------------------------------------- |
| `TestUser`, `TestGrant`, `TestStrategy` | Маленькие согласованные типы для сценариев         | Повторять типы и преобразования в каждом файле  |
| `SELF_ORIGIN`, `TARGET`                 | Одинаковый origin и защищённая цель                | Следить за совместимостью URL вручную           |
| `makeUser`, `makeGrant`                 | Создать профиль и результат входа                  | Большие повторяющиеся литералы в каждом тесте   |
| `deferred`                              | Завершить Promise в нужный момент                  | Ненадёжные задержки и setTimeout                |
| `flush`                                 | Дать цепочкам microtask продвинуться               | Случайное число await в тестах                  |
| `TestBrowser`                           | Общие locks/markers/channel для нескольких вкладок | Настоящий браузер ради любой unit-гонки         |
| `createStrategy`                        | Базовая стратегия со spies и заменяемыми методами  | Полная реализация интерфейса в каждом сценарии  |
| `createAuth`                            | Поднять сервис, платформу и журнал событий         | Повторять wiring и подписки                     |
| `createSignedIn`                        | Поднять уже восстановленную сессию                 | Один и тот же bootstrap в каждом тесте запросов |
| `createServer`                          | Принять выбранные Bearer-токены и записать попытки | Переписывать stub HTTP-поведения                |

Эти helpers делают тест читаемым: в нём остаются именно условия ошибки, а не
двадцать строк настройки. Они не должны прятать то поведение, которое проверяет тест.

## deferred: поставить сеть на паузу

`deferred<T>()` возвращает `{ promise, resolve, reject }`. Promise не завершится,
пока сам тест не вызовет resolve/reject. Можно дождаться начала refresh, выйти
из сессии и только потом «доставить» серверный ответ.

```ts
// @vitest-environment node
import { expect, it, vi } from 'vitest';

import {
  type TestGrant,
  createAuth,
  deferred,
  flush,
  makeGrant,
} from './test-kit';

it('поздний login не возвращает пользователя после logout', async () => {
  const response = deferred<TestGrant>();
  const { auth } = createAuth({
    strategy: { login: vi.fn(() => response.promise) },
  });
  try {
    const result = auth.login({}).catch((error: unknown) => error);
    await flush();
    const logout = auth.logout();
    response.resolve(makeGrant('late-token'));
    expect(await result).toMatchObject({ code: 'session_changed' });
    await logout;
    expect(auth.getSnapshot().status).toBe('guest');
  } finally {
    auth.destroy();
  }
});
```

Catch устанавливается до завершения отклоняемого Promise: иначе тестовый раннер
может заметить необработанное отклонение ещё до await expect. Такой catch возвращает
ошибку как значение только в тесте, чтобы проверить её позже.

## flush и два разных вида времени

`flush(rounds = 30)` несколько раз делает await Promise.resolve(). Это продвигает
цепочки microtask, но не перематывает setTimeout и не выполняет настоящую сеть.
Счётчик rounds — практический helper для внутренних цепочек, не доказательство,
что любая задача во всём приложении уже завершена. По возможности проверяйте
конкретный признак начала операции: spy, deferred или событие.

Есть два независимых источника времени:

- `browser.advance(ms)` меняет now тестовой AuthPlatform. Это двигает срок токена,
  backoff и время последней сверки сервиса, но не запускает JS-таймеры.
- `vi.advanceTimersByTimeAsync(ms)` двигает fake timers Vitest. Это запускает
  timeout, bootstrap retry и polling, но само по себе не меняет TestBrowser.now.

Если сценарий зависит от обоих, двигайте оба явно. Тест «refresh пора начинать»
обычно использует browser.advance; тест «истёк дедлайн зависшего refresh» — fake timers.
Стратегии, которые читают глобальный Date.now, также требуют fake system time.

## TestBrowser и несколько вкладок

Один TestBrowser содержит общие LocalLocks, маркеры и карту каналов. Каждый вызов
platform() создаёт отдельную вкладку со своей видимостью, подписками и историей
навигации. Два сервиса связаны только если им передан один TestBrowser:

```ts
const browser = new TestBrowser();
const a = createAuth({ browser });
const b = createAuth({ browser });
await Promise.all([a.auth.bootstrap(), b.auth.bootstrap()]);
await a.auth.logout();
await flush();
// Проверяйте состояние b, вызовы стратегии и события.
a.auth.destroy();
b.auth.destroy();
```

platform.resume() имитирует возвращение на вкладку; resume({ restoredFromCache: true })
— возврат из bfcache. goOnline() вызывает обработчики сети. visible=false позволяет
проверить, что скрытая вкладка не делает polling. navigated содержит адреса SSO:
тест не покидает Node-процесс при navigate.

Канал доставляет сообщения через queueMicrotask и не отправляет их самому своему
подписчику. Это похоже на нужную семантику вкладок, но не проверяет браузерное API
BroadcastChannel, sandbox, потерю сообщений и порядок реальных HTTP Set-Cookie.

## Фабрики стратегии и сервиса

createStrategy создаёт vi.fn для restore/login/renew/logout/decorate. В overrides
передавайте только то, что отличается: например, renew с deferred, restore с 401
или отсутствие renew для стратегии без обновления.

createAuth возвращает auth, strategy, browser, platform, events и eventTypes().
events заполняется через настоящую подписку сервиса, а не читается из приватных
полей. config меняет параметры сервиса. instance позволяет передать настоящий
экземпляр стратегии: spread объекта потерял бы методы её прототипа.

createSignedIn выполняет bootstrap с makeGrant, затем очищает журнал событий.
Поэтому события начального восстановления не мешают проверять дальнейший refresh.
Это удобство нельзя использовать для теста самого bootstrap: оно спрячет проверяемый шаг.

## createServer: простая модель отказа токена

Передайте допустимые токены: createServer('new-token'). send(attempt) проверяет
Authorization и отвечает объектом `{ status: 200 }` либо `{ status: 401 }`.
received хранит фактически отправленные Authorization, а send — spy.

Это удобно для проверки «первый токен отвергнут, после renew ушёл новый».
Это не HTTP-сервер: он не читает Request body, не ставит cookie, не выполняет CORS
и не проверяет серверную транзакцию. Для fetch-тела и response parsing используйте
настоящие Request/Response в adapters.test.ts; для API — серверные тесты.

## Как выглядит полезный тест гонки

1. Создайте минимальное исходное состояние.
2. Остановите конкретный внешний шаг через deferred.
3. Дождитесь, что шаг действительно начался.
4. Измените сессию/сеть/вкладку.
5. Доставьте старый результат.
6. Проверьте и итог, и запрещённое действие: токен не восстановился, чужой запрос
   не отправился, navigate не вызван, второй refresh не начался.

Не ограничивайтесь количеством строк покрытия. Тест должен падать на ошибочном
порядке событий, ради которого он написан. Не делайте helper отдельной копией
реализации сервиса — тогда одинаковая ошибка окажется и в коде, и в ожидаемом результате.

## Запуск и уборка

В тестах ядра первая строка — `// @vitest-environment node`. Завершайте созданные
сервисы через destroy, особенно если включили polling или оставили повтор bootstrap.
Возвращайте vi.useRealTimers и mocks в afterEach. Не оставляйте живой BroadcastChannel.

```bash
npm run test -w mini-jira
```

Unit-тесты проверяют управляемую модель. Отдельно нужны интеграционные проверки
реального клиента и браузерные сценарии с сервером для cookie, redirects, offline
и нескольких страниц. Наличие TestBrowser само по себе не означает наличие E2E
или production-гарантий конкретного browser runtime.
