# internal: управление асинхронной работой

[К ядру](../README.md)

Здесь нет бизнес-логики входа. Это небольшие инструменты, которые позволяют
AuthService ждать сеть, прекращать ожидание, выдерживать паузу и сохранять порядок
операций. Все production-helper этой папки находятся в `async.ts`.
`internal.test.ts` проверяет их, а также общие ошибки и нормализацию ответов из
корня lib. Имена internal означают деталь реализации, а не публичный API приложения.

## Зачем эта папка нужна

Обычное `await fetch()` отвечает только на вопрос «когда завершился этот запрос?».
Для сервиса сессии нужны дополнительные правила:

- один экран отменил запрос, но общий refresh нужен остальным;
- пользователь ждёт не дольше заданного срока, даже если сторонний callback завис;
- упавший сервер нельзя опрашивать без пауз из каждого запроса;
- медленный save старой сессии не должен завершиться после clear при выходе.

Если каждый caller будет реализовывать эти правила самостоятельно, появятся
разные таймауты, утечки listeners и очереди, останавливающиеся после первой ошибки.

## throwIfAborted(signal)

Проверяет, не отменена ли операция ещё до начала работы. Если signal уже aborted,
бросает его reason. Это полезно до prepare: не нужно начинать восстановление сессии
ради запроса, который вызывающему коду уже не нужен.

Проверка не подписывается на будущую отмену и не останавливает начатый fetch.
Для этого signal передают самому fetch либо используют abortable для ожидания.

**Без неё:** заранее отменённый запрос мог бы начать лишний refresh или другую работу.

## abortable(promise, signal): отменить ожидание, а не общую операцию

Представьте три запроса, ожидающих один refresh. Пользователь закрыл экран первого.
Если его AbortController отменит сам refresh, остальные два тоже сломаются.
`abortable` создаёт отдельное ожидание для первого запроса: оно отклоняется при
abort, но исходный Promise продолжает выполняться.

```ts
const sharedRefresh = refreshOnce();
await abortable(sharedRefresh, pageController.signal);
```

При отсутствии signal возвращается исходный Promise. При уже отменённом signal
ожидание отклоняется сразу. После завершения исходного Promise обработчик abort
удаляется; при abort одноразовый listener удаляется автоматически. Обработчики
исходного Promise могут сохранять замыкания до его завершения, поэтому общие
сетевые операции отдельно ограничены withDeadline.

Helper не создаёт AbortController для источника и не имеет возможности отменить
чужую сеть. Это ожидаемая семантика, а не ошибка.

**Без него:** отмена одного экрана либо отменяла бы refresh всех экранов, либо вообще
не освобождала бы вызывающий код от ожидания.

## withDeadline(timeoutMs, task): верхняя граница ожидания

Создаёт собственный AbortController, вызывает task(signal) и ставит таймер.
Если task не завершился вовремя, наружный Promise отклоняется с AuthError timeout,
а signal становится aborted. Таймер очищается при обычном успехе или ошибке.
Синхронный throw внутри task тоже превращается в отклонение Promise.

```ts
await withDeadline(15_000, async (signal) => {
  const response = await fetch('/api/v1/auth/refresh', {
    method: 'POST',
    signal,
  });
  // Здесь ещё нужна проверка response.ok и схемы JSON.
  return response;
});
```

Важное различие: таймаут ограничивает ожидание, а не откатывает серверную транзакцию.
Сервер мог обработать refresh раньше, чем ответ потерялся. Поэтому у сервера есть
окно повторного refresh и повторная выдача актуальной cookie.

Если task игнорирует signal, его внутренняя работа может продолжиться после таймаута.
Helper не умеет принудительно остановить произвольный JavaScript. Поздний результат
уже не завершит наружный Promise, но побочные эффекты, включая сетевые, требуют
кооперации самой реализации. Передавайте signal во все login/refresh/logout fetch.

**Без helper:** один зависший callback мог бы бесконечно держать login/refresh и
оставить все ожидающие запросы заблокированными.

## Backoff: увеличивающаяся пауза со случайным разбросом

После сбоя нельзя сразу бесконечно запускать refresh из каждого запроса.
`Backoff(baseMs, maxMs)` выдаёт паузы через next(), увеличивая верхнюю границу
вдвое до maxMs. Фактическая пауза случайна между половиной границы и всей границей.
Этот разброс называется jitter: клиенты не должны повторять запросы одновременно.

При base=1000 и max=8000 первые диапазоны примерно такие:

| Вызов next | Пауза, мс |
| ---------- | --------- |
| 1          | 500–1000  |
| 2          | 1000–2000 |
| 3          | 2000–4000 |
| 4 и далее  | 4000–8000 |

`reset()` возвращает счётчик к началу после успеха или восстановления сети.
Сам Backoff не запускает таймер и не выполняет повтор: он только вычисляет паузу.
В сервисе отдельные экземпляры используются для bootstrap и refresh, чтобы сбои
одной операции не меняли историю другой. Для refresh серверный Retry-After имеет
приоритет над локальным backoff, если он присутствует.

**Без него:** недоступный сервер получил бы лавину повторов, а батарея и сеть
пользователя тратились бы на заведомо неуспешные попытки.

## SerialQueue: порядок внешнего хранения

В памяти logout может очистить состояние мгновенно. Но внешнее хранилище может
работать асинхронно. Если `save(sessionA)` и `clear()` выполняются параллельно,
медленный save может завершиться последним и вернуть уже удалённую сессию.

SerialQueue.add(task) ставит задачу после предыдущей. `idle()` возвращает Promise,
который ждёт текущий хвост очереди. Ошибка задачи передаётся onError и при нормальной
работе обработчика не мешает следующей задаче.

```text
save(A) ── завершён ──► clear() ── завершён ──► save(B)
```

Это очередь одного экземпляра, а не межвкладочный lock. Она используется для
необязательного AuthPersistence; в браузерном mini-jira persistence токенов нет.
Если всё-таки подключаете внешнее хранилище, его операции должны завершаться;
у SerialQueue нет собственного таймаута, лимита длины или отмены. onError должен
быть безопасным: бросивший обработчик ошибок сам нарушит работу очереди.

**Без очереди:** сохранённая сессия могла бы не соответствовать текущему состоянию
после быстрого входа/выхода. Web Locks этой проблемы сами по себе не решают.

## Какие механизмы не следует путать

| Инструмент        | Что ограничивает                 | Чего не делает                            |
| ----------------- | -------------------------------- | ----------------------------------------- |
| abortable         | Ожидание одного потребителя      | Не отменяет общий refresh                 |
| withDeadline      | Время ожидания task и её signal  | Не доказывает отмену серверного изменения |
| Backoff           | Частоту следующих попыток        | Не выполняет запросы самостоятельно       |
| SerialQueue       | Порядок persistence              | Не синхронизирует вкладки                 |
| platform.withLock | Одновременность session-операций | Не заменяет проверки epoch/version        |

## Как проверять изменения

Используйте fake timers для таймаутов и deferred для порядка завершения.
Проверяйте не только возвращённую ошибку, но и побочный эффект: исходный общий
Promise продолжил работу, signal действительно aborted, таймер удалён, clear
не обогнал save. Не добавляйте реальные многосекундные sleep в unit-тесты.

`internal.test.ts` работает с `// @vitest-environment node`: этим helpers не нужен
DOM. Из приложения их импортировать обычно не требуется — вызывайте публичные
операции сервиса, в которых правильное сочетание helpers уже собрано.
